# 日次のWBS更新と翌日の作業順位

1日の終わりに、次の4つを順に行う。

1. **WBSを更新する**（進捗率・基準日・その日の作業）
2. **ペンディングを棚卸しし、影響度で優先順位を付ける**
3. **決定を待たずに進められる作業を洗い出す**
4. **翌日の作業順位を整理する**

2〜4は `build_nikkan.py` が機械で行う。
**1（WBSの更新）だけは人（当方）が判断して書く。**
`build_nikkan.py` は進捗の記録の基準日が当日でないと不適合で止まるため、
**WBSを更新しないと日次の表は作れない。** これが順序の歯止めである。

## 0　前提・入力・出力

**単体では動かない。** 対象リポジトリの次のものを前提とする。

| 要るもの | 使いどころ |
|---|---|
| `data_progress.py` | 進捗率（現時点）と、過去に報告した時点の記録 |
| `build_process_control.py` | 確認事項（正の台帳）・資料提供依頼・WBSの本体 |
| `build_nikkan.py` | 日次の表を作る。自己点検つき |
| `build_mikomiryo_santei.py` | 据え置きと月額への効き |
| `build_soan_kadai.py`／`build_chiiki_kadai_10.py` | 決着しない場合の扱い（既定値） |
| `build_mikomi_juryo_nashi.py` | 据え置きの出どころ（区分A／B／C） |
| git | その日のコミット（作業の記録） |

**入力**　当日の作業（コミット・受領資料・ご指示）、台帳の現況。
**出力**　①更新した業務工程管理表　②`output/第10期計画_日次の状況と翌日の作業順位.xlsx`
③翌日の作業順位（ご報告する場合は上位のみ）。

**判定は4つに分ける。**

| 判定 | 意味 | 扱い |
|---|---|---|
| **適合** | 確かめて問題がない | そのまま |
| **不適合** | 直さなければ日次を締められない | 直してから進む |
| **要判断** | 規則には当たるが、文脈により適否が分かれる | 人が見て決める |
| **未実施** | 読めなかった・実行できなかった | 合格にしない。理由を残す |

## 1　WBSを更新する

### 1-1　その日に何が確定したかを拾う

```bash
git -C . log --since="$(date +%F) 00:00" --format='%h %s'
git -C . log --since="$(date +%F) 00:00" --stat | head -60
```

**「何をしたか」ではなく「それにより何が確定したか」を書く。**
受領資料・ご指示・外部レビューも拾う（コミットに現れないことがある）。

### 1-2　進捗率を動かすかを決める

`data_progress.py` の `PROGRESS` は仕様書４（1）〜（12）の進捗である。

- **基準日 `KIJUNBI` は毎日進める。** 進捗率が動かない日も進める
- **進捗率を動かした業務だけ**、動きの欄（`±0pt`／`＋1pt`）を書き換える
- **進捗率を動かした日だけ**、更新前の値を `KIROKU`・`KIROKU_UGOKI` へ移す。
  動かさない日は移さない（記録は「報告した時点」を残すものであり、
  毎日の内部更新で増やすものではない）
- その日の理由を `SHINCHOKU_RIYU_R8_MM_DD` として新設する

> **過去の時点を記す資料に現時点の値を読ませない。**
> 月次の進捗報告書・議事録は `snapshot(基準日)` と `RP.draft_label_at()` を使う。
> `PROGRESS` を直接読ませると、更新のたびに過去の報告が書き換わる。

### 1-3　業務工程管理表に追記する

| シート | 書くこと |
|---|---|
| 00 | 現時点の全体状況（件数は実物から数える形になっているため、書き換えるのは文だけ） |
| 01 | 業務別の未了の理由に、その日の作業を追記 |
| 02 | 当月の工程に、成果物と実績を追記 |
| 03 | 確認事項の状態・回答・備考。**新たな論点はここへ登録する** |
| 06 | 資料提供依頼の状態 |

**新しい論点を書く前に、同じ問いが台帳にないかを語で探す。**
言い換えで二重に起票したことが実際にある。

```bash
python3 - <<'PY'
import ast, io
src = io.open('build_process_control.py', encoding='utf-8').read()
for n in ast.parse(src).body:
    if isinstance(n, ast.Assign) and any(getattr(t,'id',None)=='CHECK' for t in n.targets):
        C = ast.literal_eval(n.value)
for x in C:
    if '探したい語' in str(x[3]) + str(x[4]):
        print(x[0], x[3])
PY
```

### 1-4　作り直す

```bash
python3 build_process_control.py
```

**台帳を増減したら、件数を述べている成果品を作り直す。**
件数は実物から数える作りになっているが、**作り直さないと古い件数が残る。**

```bash
python3 tools/suchi_impact.py --map <古い件数>     # どこに残っているか
```

## 2　ペンディングの棚卸しと優先順位

```bash
python3 build_nikkan.py            # 基準日は実行した日
python3 build_nikkan.py 2026-10-01 # 基準日を指定する（さかのぼって作るとき）
```

02シートに**確認事項（決定を求めるもの）**と
**資料提供依頼（資料の提供を求めるもの）**を分けて掲げる。
いずれも**完了・了承済でないもの**を拾う。

**影響度は5つの観点で点を付ける。付け方は03シートに全て載る。**

| 観点 | 重い理由 |
|---|---|
| 期限 | 超過＋2・当月＋1。当区域はほとんどが超過か当月であり、**単独では順位が付かない** |
| 止めている成果物 | 概算＋3・保険料＋2・計画素案＋1（上限4） |
| 月額への効き | 100円以上＋4・50〜100円＋2・50円未満＋1。**最も順位を分ける** |
| 法定記載事項 | ＋2 |
| 既定値がない | ＋3。決まらないと当方の作業が止まる |
| 国の告示・公布待ち | −2。催促できない（重要でないという意味ではない） |

点が9以上を**至急**、6〜8を**優先**、5以下を**通常**とみる。

**この順位は機械が付けたものである。** 相手のご都合・会議の日程・
作業の段取りは入っていない。**人が並べ替えてよい。**
並べ替えたときは、その理由を進捗の理由に残す。

## 3　作業継続可能なものの洗い出し

04シートに2つを分けて掲げる。

- **据え置き（区分A）**　資料の受領を待たずに当方の側で確定できるもの
- **既定値で進める**　決着しない場合の扱いを置けており、決定を待たずに進めるもの

**04シートの2に「先に扱いを決めるもの」が出たら、それが最優先である。**
既定値を置けていない確認事項は、**決まらないと当方の作業が止まる。**
扱いを決めること自体が翌日の作業になる。

> 「作業継続可能」は着手できるという意味であり、
> **その作業だけで成果品が確定するという意味ではない。**
> 既定値で進めたものは、決定を受けた時点で見直す。

## 4　翌日の作業順位

05シートが、04の上位と02の至急を並べる。

- **相手のある作業（催促・照会）は午前のうちに出す。** 返事に日数がかかる
- **当方だけで進むものは午後に回してよい**
- 期限の近い成果物（第2次概算・予算編成用）から逆算する

## 5　締める

```bash
python3 build_nikkan.py                     # 自己点検が全件適合であること
python3 tools/xlsx_zuhyo_check.py output/第10期計画_日次の状況と翌日の作業順位.xlsx
python3 tools/restore_unchanged.py          # 中身の変わっていない成果品を戻す
git add -A && git commit && git push -u origin claude/daisetsu-care-plan-docs-pvjqid
```

**プルリクエストは明示の依頼がない限り作らない。**

ご報告するときは**上位だけ**にする。160件の一覧をそのままお送りしない。
発注者へ出す文章には**当方の内部の仕組み・作業経過を書かない**
（スクリプト名・「固定値では書いていません」・作業日の細かい日付）。
本表自体は**内部保管**であり、発注者への送付は想定しない。

## 6　やってはいけないこと

- **点検の準備で作業を壊さない。** `git reset --hard` を通常の手順に置かない。
  始めに版と作業の状態を**読み取りだけで**記録する
- **進捗率を上げる理由を作らない。** 動いていない日は `±0pt` と書く。
  **止まっていることを隠さない**（止まっている理由こそ翌日の作業になる）
- **台帳を二重に持たない。** 新しい論点は業務工程管理表へ登録し、
  日次の表はそこから読む
- **件数・進捗率を固定値で書かない。** 実物又はソースから数える
- **過去に報告した数値を書き換えない。** 記録へ移してから更新する

詳しい軸は `references/checklist.md`、機械で確かめる手順は
`references/commands.md`、実際に起きた誤りは `references/pitfalls.md`。
