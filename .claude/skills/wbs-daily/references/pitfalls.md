# 陥りやすい誤り（この作業で実際に起きたもの）

CLAUDE.md §4 のうち、日次のWBS更新と優先順位づけに関わるものを抜いたもの。

## 進捗と記録

- **過去の時点を記す資料に「現時点の値」を読ませない。**
  業務進捗報告書 令和8年8月分が `data_progress.PROGRESS` を直接読んでいたため、
  **8月分の報告の進捗率が再出力のたびに書き換わっていた**
  （667→806→843→896段落と3回）。
  `snapshot(基準日)`・`RP.draft_label_at(基準日)` を使う。
  **PROGRESS を更新したら、更新前の値を必ず KIROKU へ移す。**

- **記録を毎日増やさない。** `KIROKU` は「報告した時点」を残すものである。
  進捗率が動かない日に基準日だけを進めるのは、報告ではなく内部の更新であり、
  記録へ移す必要はない。**動かした日だけ移す。**

- **止まっていることを隠さない。** 作業をしても未了が減らない日は `±0pt` と書く。
  (8)各種会議への技術的支援・(9)パブリックコメント支援は、
  会議・手続が立たない限り動かない。
  **止まっている理由こそ翌日の作業になる。**

## 台帳

- **確認事項を別の成果品で起票したら、必ず業務工程管理表へ登録する。**
  `build_receipt_mieru_suikei.py` で起票したNo.127〜No.129が
  `CHECK` に入っておらず、**No.1〜No.154のうち3件が欠番**になっていた。
  `sorted(x[0] for x in CHECK)` で欠番を出せば分かる。

- **新しい論点を書く前に、同じ問いが台帳にないかを語で探す。**
  3町協議資料で町ごとの論点を新たに持とうとしたところ、
  **3町共通の4件はいずれもNo.130とNo.150の言い換え**であり、
  地域ケア会議の実績も**No.121と同じ問い**であった。

- **台帳を1つに減らさない。** 業務工程管理表（進捗の管理）と
  計画素案の別管理表（素案の章節から引く索引）は用途が異なる。
  **業務工程管理表を正とし、別管理表に対応するNo.を注記する。**

- **台帳を増減したら、件数を述べている成果品を作り直す。**
  確認事項を2件増やしたのに3冊が「171件」のまま残っていた。
  件数は実物から数える作りであったが、**作り直していなかった。**

## 件数と数え方

- **件数が0のときは、数えられているかを先に疑う。**
  `tools/check_pages.py` が表題の付け方の違いで**表を1件も見ていなかった**のに
  「紙面をまたぐ表0件」と出した。
  通いの場の件数が3件とも None になったこともある。

- **辞書の行を `for x in r` で回すとキーが返る。** 値を見るなら `r.get(…)`。
  町別の件数が3町とも0件になった。

- **空欄の判定に `is None` だけを使わない。** 空文字列のこともある。
  年度により同じ様式でも空欄の表し方が違う。
  **数値かどうかで判定する**（`isinstance(v, (int, float))`）。

- **件数・項目数を固定値で書かない。** 実物又はソースから数える。

## 優先順位

- **点が高いことと、翌日やるべきことは同じではない。**
  機械の採点は期限・止めている成果物・月額への効き・法定記載事項・
  既定値の有無しか見ていない。
  会議の日程・相手の処理に要する日数・作業の前後関係は入っていない。
  **人が並べ替えてよい。並べ替えたら理由を進捗の理由に残す。**

- **同じ相手の件は1件ずつ出さない。** 1件ずつ採点しているため、
  同じ発注者・同じ町への確認が一覧の離れた場所に出る。
  **出すときはまとめて1回で出す。**

- **「国の告示待ち」を低い点にしたのは、催促できないからである。**
  重要でないという意味ではない。報酬改定率・第1号負担割合は
  いずれも月額を100円以上動かす。

- **既定値は協議を進めるための仮置きであり、公表の確定の根拠にならない。**
  既定値で進めたものは、決定を受けた時点で見直す。

- **「決着しない場合の扱い」が無いものが最優先である。**
  決まらないと当方の作業が止まる。扱いを決めること自体が翌日の作業になる。

## 締めるとき

- **点検の準備で作業を壊さない。**
  固定のリモートブランチへの `git reset --hard` を通常の手順に置くと、
  手で直した内容を捨てたうえで別の状態の成果品を点検してしまう。
  始めに版と作業の状態を**読み取りだけで**記録する。

- **再出力しただけの成果品を戻すとき、本文の文字だけで比べない。**
  太字・改ページ・行の分割といった体裁の変更は本文の文字に現れないため、
  「変わっていない」と判定されて消える。
  `tools/restore_unchanged.py` は zip の中身で比べる。

- **走査した結果を表示するだけで終わらせない。**
  検出があっても終了コード0で終わると「通った」ことになる。
  **実行できなかった検査を「適合」に丸めない。**

- **xlsx は Markdown を解釈しない。** `**` を書くとそのまま出る。
  書き出しの時点で落とす（`_plain()`）。
