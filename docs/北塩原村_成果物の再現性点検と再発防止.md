## 1　金ヶ崎町で起きたこと

金ヶ崎町のブランチ `claude/kanegasaki-survey-review-n68hjn` を確認した。

| 項目 | 状況 |
| --- | --- |
| 追跡ファイル | 73件 |
| 本文を組み立てる生成器 `ch_*.py` | **0件** |
| 体裁ファイル | `docs/kanegasaki/style/{figs.py, figs_soan.py, fmt.py}` は追跡済 |
| 記録MD | 53本 追跡済 |
| 点検ツール | `.claude/skills/docx-design/check_docx.py` 追跡済 |
| 成果物の docx | **0件**（`output/` は xlsx のみ） |
| 最新コミット | `c42b005　失われたものの範囲を確定し、図26点を復元した` |

同じく `claude/金ヶ崎町高齢者` にも `ch_*.py` は無い。

**事象の構造**は次の一点に尽きる。

> 体裁ファイルと記録MDは追跡していたが、**本文そのものを組み立てる生成器**は
> スクラップパッド（環境ごとの一時領域）にしか置いていなかった。
> 成果物の docx もコミットしていなかった。
> よって環境が作り直された時点で、本文を作り直す素と、作り直した結果の
> 両方が同時に失われ、復元の起点が無くなった。

失ったのは「成果物」ではなく「**成果物を作り直せる状態**」である。ここを分けて
考えないと、再発防止の的を外す。

## 2　北塩原村の点検結果

同じことが起きないかを機械で確かめた。結論は**起きない**。

| 点検 | 内容 | 結果 |
| --- | --- | --- |
| C-0 | 必要なライブラリが `requirements.txt` にあり、入っている | 合格 |
| C-1 | 未追跡ファイルが無い（作業ツリーにだけ在るものを許さない） | 合格　0件 |
| C-2 | Python が全て追跡済み | 合格　25本 |
| C-3 | 成果物と生成器が対応する | 合格　生成器23本／成果物35点 |
| C-4 | リポジトリ内の絶対パスを直書きしていない | 合格 |
| C-5 | 外部資料に入手先の記録がある | 合格 |
| C-6a | 全生成器が正常終了する | 合格　22/22本 |
| C-6b | 再生成した内容が HEAD と一致する | 合格　**34/34点** |

金ヶ崎町との決定的な違いは次の2点である。

1. **本文を組み立てる生成器が追跡されている。**
   `build_kitashiobara_kosshi_rev.py`（計画素案の本文、約3,160行）と
   `build_kitashiobara_mokuji.py`（目次）がリポジトリにある。
   金ヶ崎町の `ch_*.py` に相当するものが、こちらでは追跡済である。
2. **原本と成果物の両方が追跡されている。**
   `source/北塩原村_骨子案_原本_20260731.docx` が起点として残り、
   `output/北塩原村_計画素案.docx` ほか成果物35点も追跡済である。
   起点と結果の二重の控えがあるため、片方が壊れても戻せる。

### 内容一致の判定方法

docx・xlsx は ZIP であるため、作り直すとファイル内部の生成時刻が変わり、
**バイト列は必ず変わる**。したがって一致はバイトではなく内容で判定する。

* docx … （段落数、表数、本文テキストの SHA-256 先頭12桁）
* xlsx … （シート数、値のあるセル数、値の SHA-256 先頭12桁）
* png　… （長さ、SHA-256 先頭12桁）

計画素案での実測は `段落416／表117／7c9f1cd05b26` で、HEAD と再生成が一致した。

## 3　点検で見つけた3つの弱点と、その手当て

点検は合格したが、放っておけば同種の事故になりうる弱点が3つ見つかった。
いずれもこの作業で手当てした。

### (1) ライブラリの欠落で成果物が静かに欠ける　【実際に起きた】

`build_component_images.py` は Pillow（`import PIL`）を使うが、環境を
作り直した後の環境には Pillow が入っていなかった。この生成器だけが落ちると、

* `output/00_全計画マスター管理表.xlsx` … シート11→10、セル782→752
* `output/01_共通_基本コラム部品.xlsx` … シート8→7、セル314→284

と、画像シートが**欠けた成果物が何の警告もなく出来上がる**。他の21本は正常
終了するため、気づかずに配布する危険があった。

**手当て**
* `requirements.txt` を追加（openpyxl／python-docx／Pillow と、確認した版）。
* 点検 C-0 で、必要なライブラリが入っているか・`requirements.txt` に
  書かれているかを実行前に確かめる。欠けていれば `pip install -r` の指示を出す。

### (2) 外部資料の消失に対して案内が無かった

`build_fukushima_seishin_extract.py` が読む NDB集計2点は既に消えていた。

| ファイル | 状況 |
| --- | --- |
| `Tables_f2013_2023_ver1.0.xlsx` | 消失（アップロード置き場にあった） |
| `Tables_f2023_kohi_ver1.0.xlsx` | 消失（同） |

ただしこれは**意図した判断**である。1ファイル20MB前後あるため格納せず、
代わりに成果物 `output/福島県_精神医療指標抽出.xlsx` を追跡し、入手先URLを
`docs/北塩原村_長期入院患者基盤整備量_資料充足性確認.md` に記録していた。
計画本文の執筆はこの成果物を参照して進むため、作業は止まらない。

問題は、再実行したときに「抽出元ファイルが1つも見つかりません」という
手がかりの無い停止になることだった。

**手当て**
* 置き場所の候補を `source/精神保健/NDB/` → アップロード置き場の順に探すよう変更。
  再入手したものをリポジトリ内に置けば、以後は引数なしで動く。
* 見つからないときは、入手先URL・必要なファイル名・置き場所・引数での
  指定方法を示して停止するようにした。
* 成果物の `00_概要` シートに、抽出元の**大きさと SHA-256** を記録するようにした。
  再入手した原典が同一かを後から確かめられる。

### (3) 生成器が絶対パスを直書きしていた

`/home/user/repository` を直書きしている箇所が9ファイル13か所あった
（`kitashiobara_common.py` の `OUT_DIR` を含む）。別の場所にチェックアウトして
生成器を動かすと、**出力が元の場所に書き戻される**。

この弱点は点検そのものを誤らせた。最初にクリーンルーム検証としてリポジトリを
別の場所に複製して生成器を動かしたところ「正常」と出たが、実際には出力が
元のリポジトリに書かれていただけで、複製側は何も検証していなかった。

**手当て**
* 全ファイルで `REPO_ROOT = os.path.dirname(os.path.abspath(__file__))` から
  基準を求める形に変更。`kitashiobara_common.py` に `REPO_ROOT`・`SRC_DIR` を追加。
* 点検 C-4 で、リポジトリ内を指す絶対パスの直書きが復活しないよう見張る。
* 変更後に全22本を再実行し、34/34点が内容一致することで、この書き換えが
  成果物を変えていないことを確かめた。

## 4　再発防止の仕組み

### 点検ツール `check_reproducibility.py`

```
python3 check_reproducibility.py              静的点検のみ（数秒）
python3 check_reproducibility.py --regenerate 作り直して内容を照合（約2分）
```

不合格があれば終了コード1を返すため、作業の節目に機械的に挟める。
このツール自身も、追加した時点で未追跡だったため C-1・C-2 が自分を検出した。
点検が効いていることの実例である。

### 生成器と成果物の対応表

`check_reproducibility.py` の `BUILDERS` に、生成器23本と成果物35点の対応を
**依存の順**で書いた。これは点検の材料であると同時に、環境を作り直したときの
手順書そのものになる。順序に意味があるのは次の箇所である。

| 順 | 生成器 | 理由 |
| --- | --- | --- |
| 1 | `build_excel.py` | 管理表の本体を作る |
| 2 | `build_component_images.py` | 1の成果物に画像を貼る |
| 3 | `build_kitashiobara_projection.py` | 将来推計 |
| 4 | `build_kitashiobara_mikomiryo.py` | 3の計算を runpy で取り込む |
| 5 | `build_kitashiobara_kosshi_rev.py` | 計画素案の本文 |
| 6 | `build_kitashiobara_mokuji.py` | 5と同じファイルに目次を入れる |
| 7 | `build_kitashiobara_gaiyou.py` | 概要版 |
| 8 | `build_kitashiobara_review.py` | 5を読んで網羅性を見る |
| 9 | `build_kitashiobara_taihi.py` | 5と7を読んで前回と対比する |
| 10 | `build_shinchoku_hyo.py` | `build_kitashiobara_progress.py` を取り込む |

対応表に無い生成器や、生成器の無い成果物は C-3 が検出する。手作業で置いた
ファイル（＝作り直せないファイル）が `output/` に混ざることを防ぐ。

### 環境を作り直したときの手順

```
git clone <リポジトリ> && cd repository
git checkout claude/kitashiobara-disability-plan-order-36oyd1
pip install -r requirements.txt
python3 check_reproducibility.py --regenerate
```

最後の行が「すべて合格」で終われば、成果物は完全に復元されている。

## 5　金ヶ崎町への申し送り

北塩原村での手当てはそのまま金ヶ崎町にも使えるが、**実施は金ヶ崎町の
ブランチで行うべき作業**であり、本ブランチからは触れていない。
あちらで進める際の要点は次の3点である。

1. **復元が先、仕組みが後。**
   `ch_*.py` が無く成果物 docx も無い現状では、点検ツールを入れても
   「復元できない」と報告するだけである。まず控えの docx を起点に
   生成器を組み直す必要がある。
2. **`ch_*.py` の追跡は妥当。**
   テキストであり容量も小さい。北塩原村では本文生成器
   `build_kitashiobara_kosshi_rev.py`（約3,160行）を追跡しており、
   それが復元可能性の決め手になっている。
   CLAUDE.md の「本文はスクラップパッドに置く」方針の変更になるため、
   変更はご了解をいただいてから行うのが筋である。
3. **成果物の docx も併せて追跡する。**
   北塩原村では原本と成果物の両方を追跡しており、生成器が壊れても
   成果物から読み直せる。起点と結果の二重の控えが効く。
   金ヶ崎町は生成器も成果物も無かったため、片方からの復元ができなかった。
