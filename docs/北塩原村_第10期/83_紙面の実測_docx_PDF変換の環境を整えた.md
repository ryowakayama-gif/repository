# 紙面の実測（令和8年10月10日）― docx→PDF 変換の環境を整えた

これまで本環境では docx を PDF に変換できず、頁数は `estimate_pages.py`／
`estimate_layout.py` がレイアウト値から積み上げた**推定**だけであった。
doc77〜doc82 には毎回「紙面の目視確認は未実施」と断りを付けていた。

本日、`libreoffice-writer` と `poppler-utils` を入れ、変換と実測ができるようになった。
実測の結果、**推定の前提に3件の誤りが見つかり、分量の見通しが変わった。**

| 作ったもの | 置き場所 |
|---|---|
| 変換と実測の道具 | `scripts/render_check.py` |
| 紙面の前提を固定する点検 | `scripts/verify_soan.py` 点検68 |

| | 変更前 | 変更後 |
|---|---|---|
| 計画素案の頁数 | 推定132頁 | **実測137頁**（推定135頁） |
| 計画書の頁数 | 推定118頁＋前付4頁＝122頁 | **実測120頁＋前付4頁＝124頁** |
| 削減案をすべて行った場合 | 109頁（許容110頁の範囲内） | **111頁（許容110頁に1頁足りない）** |
| 計画素案の自己点検 | 67件 | 68件（うち不適合1件＝点検52） |

## 1　環境を整えた

### 1-1　足りなかったもの

`/usr/bin/soffice` はあったが `libreoffice-writer` が入っておらず、
Writer の文書として開けなかった。PDF を扱う `pdftoppm`／`pdfinfo` も無かった。

```
apt-get update && apt-get install -y libreoffice-writer poppler-utils
```

変換は docx スキルの `scripts/office/soffice.py` の `run_soffice()` を通して呼ぶ。
この環境は AF_UNIX ソケットが塞がれており、素の `soffice` ではユーザー
プロファイルを作れずに終わる。同スクリプトはシムと一時プロファイルを扱う。

### 1-2　フォントの置換に手当てした

**游ゴシックはこの環境に無い。** 何もしないと、和文が WenQuanYi Zen Hei、
欧文が DejaVu Sans に分かれて置換される。DejaVu Sans の数字は全角比0.64と広く、
数字の多い本計画では**紙面が3頁ぶん膨らんだ**（143頁）。

fontconfig で游ゴシックを IPAゴシックに寄せた。IPAゴシックは欧文が半角固定
（全角比0.50）で、游ゴシックに近い。これで140頁になった。

| 字 | 置換なし（DejaVu Sans） | IPAゴシック | 推定の前提 |
|---|---|---|---|
| 数字 | 0.640 em | **0.500 em** | 0.50 |
| 漢字 | 1.000 em | **1.000 em** | 1.00 |

`render_check.py --setup` がこの別名を書く。

## 2　実測して、推定の前提の誤りが3件見つかった

PDF から用紙・余白・行送り・表の幅・字幅を実測し、推定の前提と突き合わせた。

| 前提 | 実測 | 判定 |
|---|---|---|
| 本文の行送り 300 twip＝15.00pt | 15.00pt | 合う |
| 本文の高さ 14002 twip＝700.1pt | 700.09pt | 合う |
| 図の高さの合計 143,106 twip | 143,120 twip | 合う |
| 見出し・図の題・出典の行数 | すべて一致 | 合う |
| 注記の枠の高さ 11.0頁 | 11.1頁 | 合う |
| **表の幅 9638 twip（本文幅）** | **9360 twip（468.0pt）** | **★誤り** |
| **表の1行の下駄 120 twip** | **127 twip（1行18.35pt）** | **★誤り** |

### 2-1　表の幅に本文幅を使っていた（★1件目）

`build_*_docx.js` はどれも `const TBLW = 9360` で表を組んでいるのに、
`estimate_pages.py` は本文幅 `BODY_W = 9638` でセル幅を出していた。
**実際より3%広いセルを前提に折り返しを数えていた**ため、表の行数を少なく
見積もっていた。素案の表は1,371行あり、117行ぶん少なく数えていた。

`TBLW = 9360` を `estimate_pages.py` に置き、両方の推定（素案・委員会資料）で用いる。

### 2-2　行の下駄が罫線のぶん足りなかった（★2件目）

セルの上下余白は宣言どおり60＋60＝120 twip だが、実測の行高は
1行18.35pt・2行30.35pt・3行42.35pt であった。1行あたり12.00pt（240 twip）は
合っており、下駄が6.35pt（127 twip）である。差の7 twip は罫線である。
1,371行では約1万 twip（0.8頁）になる。

### 2-3　`flow()` の「頁超」に死にコードがあった（★3件目）

1頁に収まらない表を数える分岐に `page += int(...) if False else 0` が残っていた。
**前のセッションで2回同じものを書いて整理したが、3か所目が残っていた。**
送りの数え方も下の分岐と違っていたため、同じ数え方に揃えた。
（この5件は結果として頁数を変えなかったが、頁の境目の位置が変わり得る。）

## 3　行送りが Word でフォント次第になっていた（★4件目）

これは実測ではなく、docx の XML を読んで見つけた。

`spacing: {line: 300}` と書いていたが **`lineRule` を指定していなかった。**
OOXML の既定は `auto` であり、`w:line` は twip ではなく
**「1行の高さの240分の1」倍**として読まれる。つまり 300 は「1.25行」である。

- LibreOffice は twip として扱ったため、実測は 15.00pt ちょうどで推定と合った
- **Word は倍率として読む。** 1行の高さはフォントの ascent＋descent＋lineGap で
  決まるため、**游ゴシックが入っている村の Word では行送りが変わり、頁数も変わる**

游ゴシックは行間を広く取る作りである。auto のままでは、110頁の枠に収まるか
という判断そのものが当てにならない。

4つの `build_*_docx.js` の、行送りを指定している15か所すべてに
`lineRule: LineRuleType.EXACT` を付けた。これで `w:lineRule="exact"` が書かれ、
本文は15pt・表は12pt・注記は14ptにどの環境でも固定される。
10.5ptの字に15ptの行は1.43倍であり、字が切れることはない。

**組み直した後の実測は140頁のまま**で、LibreOffice 側の紙面は変わっていない。
変わるのは Word 側である。

### 3-1　既定の書体を宣言していなかった（あわせて直した）

`build_soan_docx.js` だけが `styles.default.document.run` を宣言しており、
委員会資料・照会票・照会票の束は宣言していなかった。第3回資料の実測で
**12文字が Liberation Serif（欧文の明朝）で出ていた。** 3つに宣言を加え、
すべて IPAゴシック（村では游ゴシック）になった。

## 4　分量の見通しが変わった

### 4-1　推定はなお2頁少ない

前提の誤りを直した後も、推定と実測には2頁の差が残る。

| | 推定 | 実測 | 差 |
|---|---|---|---|
| 計画素案（本文） | 135頁 | **137頁** | +2 |
| 計画書（編集注記と5-12を除く） | 118頁 | **120頁** | +2 |

節ごとに突き合わせると、推定は実紙面を±2頁で追えている（57節中、
一致18節・1頁差16節・2頁差23節）。残る差は**送り（keepNext）による空白**である。
この推定は送りの空白を実際より小さく見るため、**下限である。**

`estimate_layout.JITSU_SA = 2` として置き、分量の判定（点検52・
`estimate_sakugen.py`）ではこの差を乗せる。

### 4-2　削減案が村の許容に1頁届かなくなった

| | これまで | 実測を踏まえて |
|---|---|---|
| 何も行わない | 122頁 | **124頁** |
| 案A〜Lをすべて行う | 109頁 | **111頁** |
| 村が許容する頁数 | 110頁 | 110頁 |
| 余裕 | +1頁 | **−1頁** |

**点検52が不適合になった。** これは点検の誤りではなく、分量が実際には
許容に収まっていないことを示している。足りない1頁の当て方は3つある。

1. **下が大きく空いている頁を詰める。** `render_check.py --aki` が実紙面から
   拾う（§4-3）。上位3頁だけで2.6頁ぶんある
2. 1頁に収まらない表（3-5 28行・4-6 17行・資8 28行）を分けるか詰める
3. **村に111頁の可否を諮る**（許容110頁は10月10日の口頭のご判断）

1と2は当方で行える。**Ⅱ-113（削減案の組み合わせの対応表）で試す。**

### 4-3　実紙面の空白を拾う道具を作った（`--aki`）

推定の「送りによる空白」は当てにならない（§5）。実紙面から頁の下の空白を
測る `render_check.py --aki` を作った。計画書（120頁）の結果は次のとおりで、
**空白の合計は9.3頁ぶん**である。

| 頁 | 空白 | 割合 | 何が起きているか |
|---|---|---|---|
| 11 | 641pt | 92% | **1-8の5 の出典（3行）だけが頁に取り残されている。** 前の表が頁いっぱいに終わり、出典が入らず次頁へ送られた。次は第2章で改頁するため、この頁には出典しかない |
| 42 | 606pt | 87% | 3-4 の施策体系図が1頁の図版（`figTall`）として改頁されるため、**見出し「3-4 施策の体系」だけが前の頁に取り残されている** |
| 107 | 560pt | 80% | 5-7 の感応度の説明の後、次の要素が入らず送られた |
| 123 | 397pt | 57% | 資9 の末尾。最終頁であり、詰める対象ではない |
| 68 | 277pt | 40% | 施策4-4 の後 |

11頁と42頁は**取り残し**であり、紙面として直すべきものである。
42頁は見出しと図版が離れており、読み手にも分かりにくい。
この2つを直せば足りない1頁は出る。直し方はⅡ-113で決める。

## 6　この変換でできないこと

**Word＋游ゴシックの紙面そのものではない。** 確かめられたのは次までである。

- 用紙・余白・本文の高さ・行送り・表の幅・字幅が推定の前提と合っていること
- 頁の境目に何が来るか、表がどこでまたぐか、空白がどこに出るか
- 色・罫線・網掛け・図の見え方

確かめられないのは次である。

- **游ゴシックでの字送りと禁則処理。** IPAゴシックは数字0.5em・漢字1.0emで
  推定の前提と一致するが、欧文の字送りと行末の追い込みは書体により違う。
  なお±1〜2頁動き得る
- 目次のフィールド。LibreOffice では空のまま出る（Word で開いて更新すると
  2頁程度になる）。前付4頁の見積もりはこれを見込んだもの

村側で Word で開いて実際の頁数を確かめていただく必要がある（確認事項に起票済み）。

### 7-1　点検68を新設した（紙面の前提が build 側と一致すること）

同じ食い違いを二度起こさないため、次を機械で固定した。

`lineRule` を1か所外しても不適合になる。

### 7-2　点検52を高さで見る形に改めた

点検52は各案について「削っても頁が減らない」ことを不適合としていた。
表の幅と行の下駄を直して頁の境目が動いた結果、**案D・L・Kが単独では0頁になった。**
中身は現に減っているため、これは案が空であることの証拠にならない。

高さ（twip）で見る形に改めた。指す小見出しが空のときだけ0になる。
単独で0頁の案は、不適合ではなく注記として示す。
